• Container Queries reagieren auf die Größe eines Elternelements, nicht auf das gesamte Viewport-Fenster.
  • Sie machen HTML-Komponenten unabhängig vom globalen Layout und fördern ihre Wiederverwendbarkeit.
  • Sie sind daher besonders nützlich für komplexe, modulare Layouts wie Karten, Widgets oder wiederverwendbare UI-Komponenten.
  • Allerdings muss das Elternelement mit container-type als Container deklariert werden.
  • Für so gekennzeichnete Elternelemente gelten dann andere Regeln, wie ihre Breite/Höhe ausgerechnet wird.

    Problemstellung

    Media Queries zählen seit ihrer Einführung zu den Arbeitspferden des Responsive Webdesigns. Endlich war es auf einfache Weise möglich, die Eigenschaften des Ausgabegeräts abzufragen und das Layout einer Webseite dynamisch an diese anzupassen, anstatt wie bisher üblich, mehrere Versionen derselben Seite für unterschiedliche Geräte zu programmieren. Doch genau hier liegt auch das Problem von Media Queries: Sie prüfen das Ausgabegerät, in der Regel also den Bildschirm bzw. den Viewport des Browsers1, nicht aber den Platz, den ein konkretes Element an seiner konkreten Position tatsächlich zur Verfügung hat.

    Warum ist das ein Problem? Baut man eine vergleichsweise einfache Webseite aus einem Guss, so wie wir das bisher immer gemacht haben, kommt man mit Media Queries tatsächlich sehr weit. Man hat ein bestimmtes Layout vor Augen und weiß genau, wie viel Platz für welche Inhalte an welcher Stelle vorgesehen ist. Mit Media Queries stellt man lediglich sicher, dass das Layout nur dann angewandt wird, wenn in der Regel der Bildschirm groß genug dafür ist. Problematisch wird es allerdings, wenn das Layout selbst gar nicht statisch ist, sondern sich zum Beispiel durch Ein- und Ausblenden optionaler Inhalte selbst verändern kann. Dann kann es sein, dass durch die zusätzlich eingeblendeten Inhalte der für ein Element zur Verfügung stehende Platz nicht mehr ausreicht – ein Fall, der mit Media Queries nicht abgefragt werden kann. Die Bildschirmgröße bleibt ja immer gleich.

    Hinzu kommt, dass man in der Realität häufig gar nicht weiß, an welcher Stelle ein bestimmter Inhalt später angezeigt werden wird und wie viel Platz dann zur Verfügung steht. Als Beispiel stelle man sich hier die Teilen-Funktion von YouTube vor, die es ermöglicht, ein Video mit einem HTML-Schnipsel in fremde Webseiten einzubetten. Oder die Teilen-Funktion von Facebook, X und Instagram, mit denen ein Social-Media-Post in eine Webseite eingebettet werden kann. Aber auch, wenn man mit einem Komponenten-Framework wie Angular oder React quasi seine eigenen HTML-Elemente baut2, kann es sein, dass man während der Entwicklung noch nicht weiß, wer diese Elemente wo einsetzen wird.

    Container Queries, die seit dem Jahr 2023 von allen gängigen Browsern unterstützt werden, können helfen, diese Probleme zu lösen. Denn sie prüfen nicht das Ausgabemedium oder den Viewport des Browsers, sondern konkrete HTML-Elemente, so wie sie tatsächlich auf einer Seite dargestellt werden. Dadurch wird es möglich, CSS-Regeln zu definieren, die von Fragen abhängen wie:

    • Habe ich an dieser Stelle genügend Platz für den Inhalt?
    • Ist der zur Verfügung stehende Bereich höher wie breit oder breiter wie hoch?
    • Und viele mehr, die sich auf das gewünschte Elternelement beziehen.

    Der Vorteil: Komponenten können flexibel in unterschiedlichen Kontexten wiederverwendet werden. Zum Beispiel kann so eine Karten-Komponente innerhalb einer schmalen Sidebar anders als im breiten Hauptbereich dargestellt werden, ganz egal, auf welchem Bildschirm dies später erfolgt – es zählt nur der Platz, den man für die Kartendarstellung tatsächlich gerade zur Verfügung hat.

    1 Der Viewport ist der Anzeigebereich im Browser, innerhalb dessen die Webseite dargestellt wird.

    2 Stark vereinfachte Darstellung. 🙂

    Grundlegende Syntax

    Die grundlegende Syntax von Container Queries ist dieselbe wie bei Media Queries. Lediglich statt @media schreibt man @container und hängt dann die zu prüfenden Eigenschaften an. Zum Beispiel:

    .google-maps { /* CSS-Regeln für die KLEINE Kartendarstellung */ } @container (min-width: 30em) { .google-maps { /* CSS-Regeln für die GROSSE Kartendarstellung */ } }

    Doch auf welches HTML-Element bezieht sich diese Prüfung? Die Größe von welchem Element wird damit geprüft? Tatsächlich, so wie es dasteht, von keinem. Denn das zu prüfende Element muss zusätzlich markiert werden, damit klar ist, um welches Element es sich handelt und welche Eigenschaften tatsächlich davon abgefragt werden dürfen. Dies geschieht mit der CSS-Eigenschaft container-type. Das vollständige Beispiel lautet daher:

    main { /* Von diesem Element kann die Breite geprüft werden */ container-type: inline-size; } .google-maps { /* CSS-Regeln für die KLEINE Kartendarstellung */ } @container (min-width: 30em) { .google-maps { /* CSS-Regeln für die GROSSE Kartendarstellung */ } }

    Die Eigenschaft container-type besitzt dabei folgende Ausprägungen:

    normal Standardwert – das Element ist kein Container und kann nicht für Container Queries genutzt werden.
    size Das Element ist ein voller Container: Sowohl Breite als auch Höhe können abgefragt werden.
    inline-size Das Element ist ein einfacher Container, der nur die Inline-Achse (meist die Breite) berücksichtigt. Dies ist der in der Praxis am häufigsten genutzte Wert.
    block-size Beobachtet nur die Block-Achse (meist die Höhe).

    Diese Kennzeichnung ist notwendig, weil die Breite und Höhe eines Elements meistens von seinem Inhalt abhängen. Doch hier wollen wir ja gerade den Inhalt anders darstellen, abhängig davon, wie breit oder hoch das Element ist. Die Kennzeichnung sorgt dafür, dass die gewünschten Eigenschaften abgefragt werden können, dafür aber nicht mehr vom Inhalt des Elements abhängen. Stattdessen müssen die Breite und die Höhe dann explizit gesetzt werden, entweder mit den entsprechenden CSS-Eigenschaften (width, height, …) oder durch eine umgebende Flexbox etc.

    Mehrere benannte Container

    Häufig kommt es vor, dass man nicht den Container Query zur Prüfung des Elternelements benötigt, sondern mehrere Queries zur Prüfung mehrerer Elternelemente. Eben, weil es mehrere Stellen in einer Webseite gibt, an denen sich der zur Verfügung stehende Platz dynamisch ändern kann. Dies würde mit der oben gezeigten Syntax nicht unterstützt werden, da die einzelnen Bereiche nicht auseinander gehalten werden könnten. Die Lösung hierfür bietet die CSS-Eigenschaft container-name, wie im folgenden Beispiel gezeigt:

    #sidebar { container-name: sidebar; container-type: inline-size; } main { container-name: main; container-type: inline-size; } @container sidebar (min-width: 25em) { /* Sidebar ist mindestens 25em breit */ } @container main (min-width: 60em) { /* Hauptbereich ist mindestens 60em breit */ }

    Wie man sieht, kann den Containern mit container-name ein eindeutiger Name gegeben werden, auf den sich die eigentliche @container-Anweisung später beziehen kann.
